# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

- **Backend**: Node.js (ESM) + Express 5 + Prisma ORM + SQLite, in `backend/`.
- **Frontend**: React 18 + Vite (plain JS, not TS) + react-router-dom + axios + recharts, in `frontend/`.
- Auth: bespoke JWT (7-day expiry), token stored in frontend `localStorage`. No sessions/cookies.

## Running the app

- `npm run dev` from the repo root starts both backend (port 3001) and frontend (port 5173) concurrently.
- Fresh clone setup: `backend/prisma/dev.db` is gitignored, so run `npm run db:migrate` then `npm run db:seed` inside `backend/` before the API has any data.
- Required env vars live in `backend/.env` (gitignored, no `.env.example` exists): `DATABASE_URL`, `JWT_SECRET`, `PORT`.

## Data model

- `Asset.quantity` and `Asset.averagePrice` are **not stored columns** — each purchase is its own `Purchase` row (`quantity`, `price`, `date`), and the asset's total quantity / weighted average price are derived at read time via `aggregatePosition()` in `backend/src/services/purchases.js`. This mirrors how `Dividend` already works (a separate table keyed by `assetId`), and exists so multiple buys of the same ticker never get flattened into one misleading row. `assetController.js` (`list`/`getById`/`update`) and `dashboardController.js` all call `aggregatePosition` on the asset's `purchases` **and** `sales` before using `quantity`/`averagePrice` — if you add another place that reads an asset's position, do the same instead of trusting a stored field or calling `aggregatePurchases` alone (that one ignores sales; `create()` is the only caller that still uses it directly, since a brand-new asset can't have sales yet). `POST /api/assets` accepts an optional `quantity`/`averagePrice`/`purchaseDate` to create the *first* purchase in the same call; further purchases go through `POST /api/purchases/:assetId`.
- **`Sale` (2026-07) is the sell-side counterpart to `Purchase`** — same shape (`quantity`, `price`, `date`, `assetId`), same per-asset CRUD pattern at `/api/sales/:assetId` (`saleController.js`/`routes/sales.js`), plus `listAll`/`createForTicker` at `/api/sales` (no `:assetId`) mirroring `purchaseController`. `aggregatePosition(purchases, sales)` computes net quantity as bought-minus-sold, but keeps the average price from the buy side only (average-cost-basis accounting: selling reduces quantity, not the average cost of what's left — there's no FIFO/LIFO lot tracking). Both `saleController.create` and `createForTicker` reject a sale that would push quantity negative (`quantity > available` → 400) and 404 if the ticker doesn't already exist as an asset (unlike purchases, sales never auto-create one). `Transactions.jsx` is the only frontend consumer so far — `AssetDetail.jsx` still only shows that asset's `Purchase` history, not `Sale`.
- **`Asset.currentPrice` is a plain manually-edited column, not fetched by the app itself.** There used to be a brapi.dev/CoinGecko/StatusInvest integration inside the backend for this (removed 2026-07 due to brapi requiring a paid token and rate-limiting to 1 ticker/request, and StatusInvest's scraping being fragile) — the user still edits it inline from the Dashboard page (`frontend/src/pages/Dashboard.jsx`): a pencil icon next to "Current Price" opens a number input, saved via `PUT /api/assets/:id` with `{ currentPrice }`. It defaults to the purchase price when an asset/first-purchase is created (`assetController.create`, `purchaseController.createForTicker`) so it's never silently `0`. For `CRIPTO` assets it's entered and stored in **USD** (like `Purchase.price`/`Sale.price`); for everything else it's BRL — see the currency gotcha below.
- **Automatic price fetching was reintroduced 2026-09, at the user's request, but outside the app.** `backend/scripts/update-prices.js` takes a `{TICKER: price}` JSON map and writes it straight into `Asset.currentPrice` for a given user (matched by email), using Node's built-in `node:sqlite` module instead of Prisma Client — Prisma Client here is generated for `darwin-arm64`, and the automation that calls this script runs from a Linux ARM environment where that engine binary doesn't load, so the script bypasses Prisma entirely. It also sets `PRAGMA locking_mode=EXCLUSIVE` before writing — the automation reaches `dev.db` over a network/bridge-mounted filesystem where SQLite's default locking scheme fails with `disk I/O error` on write, even in `journal_mode=OFF`; exclusive locking mode is the one mode that works there. The script itself never fetches prices — a daily scheduled task fetches them from Yahoo Finance's public per-ticker chart endpoint (`query1.finance.yahoo.com/v8/finance/chart/<TICKER>.SA?range=1d&interval=1d`, reading `chart.result[0].meta.regularMarketPrice`) for `ACAO`/`FII`/`ETF`/`BDR` tickers and CoinGecko's free `simple/price` endpoint for `CRIPTO` tickers, both keyless, then calls this script with the results — avoiding the token/rate-limit and scraping-fragility problems that got the old integration removed. `RENDA_FIXA` (Tesouro Direto) assets are intentionally excluded — no simple market-quote source for those. Writes go straight to the DB file, not through the API, so they bypass JWT auth and `PUT /api/assets/:id` entirely; keep that in mind if `update()`'s validation (in `assetController.js`) ever grows a rule this script should also respect.
- **`GET /api/dashboard` only includes assets that have at least one `Purchase`** (`dashboardController.overview` filters `allAssets` down to `assets` on `purchases.length > 0`) — the dashboard is meant to mirror real positions from the Purchases page, not stock-watchlist entries created with just a ceiling price and no actual buy. `GET /api/assets` (used by `AssetDetail.jsx`/asset lookups) is intentionally unfiltered. Its response fields are `alerts`, and each `assetList` entry has `priceChange`, `returnPct`, `balance`, `percentPortfolio` (renamed from Portuguese `alertas`/`variacao`/`rentabilidade`/`saldo`/`percentCarteira` during the 2026-07 English pass — keep backend and `Dashboard.jsx` in sync if you touch these).
- `backend/prisma/seed.js` inserts one `Purchase` row per line item in the Excel "Compras" sheet (not aggregated), so `npm run db:seed` reproduces real transaction-level history. Importing `seed.js` (e.g. from a test) does **not** run `main()` — it's guarded by an `import.meta.url` check — so tests can safely import `excelDateToJS` without wiping the dev database.
- `PUT /api/purchases/:id` (`purchaseController.update`) lets a single purchase's `quantity`/`price`/`date` be corrected without deleting and recreating it — it does *not* allow changing which asset/ticker it belongs to (do that by deleting and re-adding). Same shape for `PUT /api/sales/:id`.
- Frontend page `frontend/src/pages/Transactions.jsx` (route `/transactions`, formerly `Purchases.jsx` at `/purchases`/`/compras`/`/ativos`) is a flat, ungrouped list of every `Purchase` **and** `Sale` row across all assets — not one row per ticker. It fetches `GET /api/purchases` + `GET /api/sales` client-side and merges/sorts them, tagging each row `BUY`/`SELL`. The "New Transaction" form's Type selector picks the endpoint (`POST /api/purchases` vs `POST /api/sales`, both upsert-or-require-existing by ticker in the body, no `:assetId`). The per-ticker aggregate view (with dividends and that ticker's own purchase history) still lives at `/assets/:id` (`AssetDetail.jsx`) — it doesn't show `Sale` rows yet.
- **The project's UI/code language was translated to English in 2026-07, but `Asset.category` (`ACAO`, `FII`, `ETF`, `BDR`, `CRIPTO`, `RENDA_FIXA`) and `Dividend.type` (`DIVIDENDO`, `JCP`, `RENDIMENTO`) values stored in the database are still Portuguese** — this was a deliberate choice to avoid a risky data migration on the user's real portfolio data. The frontend translates them to English purely for display via label maps (`CATEGORY_LABELS` in `Dashboard.jsx`/`Purchases.jsx`, `DIVIDEND_TYPE_LABELS` in `AssetDetail.jsx`) — don't assume the raw `category`/`type` string from the API is already in English.
- **`Dividend.quantity` and `Dividend.unitPrice` are optional context fields, not the source of truth for `amount`.** They mirror the "Quantidade"/"Preço unitário" columns on a B3 (Brazilian exchange) statement export, added so dividends logged from that report keep the same detail as a Purchase. `amount` (the "Valor da Operação" column) must still be entered/stored explicitly — for JCP specifically, Brazil withholds income tax at the source, so `amount` is *not* `quantity * unitPrice`. Don't add a computed-amount shortcut that assumes otherwise.

## Gotchas

- **Price cache**: `backend/src/services/prices.js` holds a 5-minute in-memory cache (`usdBrlCache`) for the USD/BRL exchange rate only (used to convert crypto `averagePrice`, which is stored in USD, to BRL for display). It's process-local and resets on every restart — which happens on every save since `backend` runs via `node --watch`. `fetchUsdBrl` falls back to a hardcoded `5.50` BRL/USD rate if the AwesomeAPI call fails and there's no cached value.
- **Crypto is USD end-to-end; BRL only shows up for portfolio-wide totals.** For `CRIPTO` assets, `Purchase.price`/`Sale.price`/`Asset.averagePrice`/`Asset.currentPrice` are *all* in USD (2026-07 — `currentPrice` used to be entered in BRL, which silently broke `priceChange`/`returnPct` once `dashboardController` started comparing it against a BRL-converted average price; if you ever see a crypto asset with a wildly wrong return %, suspect a stale BRL value sitting in `currentPrice` and re-save it in USD). `Dashboard.jsx`/`AssetDetail.jsx` render crypto rows with `fmtUsd`/`fmtA` (USD, no conversion) instead of the BRL formatter used everywhere else — don't route crypto prices through `fmt()`. `dashboardController.js` still converts both `averagePrice` and `currentPrice` to BRL internally (`avgPriceBrl`/`currentPriceBrl`) via the live `usdBrl` rate, but only to fold crypto into the portfolio-wide BRL totals (`totalInvested`, `totalCurrent`, `byCategory`, `alerts` ceiling comparison) — those BRL variants aren't meant for per-asset display.
- **Frontend API base URL is hardcoded** in `frontend/src/services/api.js` (`http://localhost:3001/api`), not env-driven — won't work in any non-localhost deployment without a code change.
- Asset categories (`ACAO, FII, ETF, BDR, CRIPTO, RENDA_FIXA`) and dividend types (`DIVIDENDO, JCP, RENDIMENTO`) are free-text strings in Prisma, not enums.

## Conventions

- `backend/` has a Vitest suite (`npm test` inside `backend/`, pinned to `vitest@^2` — v4 requires Node ≥20.19/22.12 and fails to start on this machine's Node 20.11). No frontend test suite exists yet. Both `backend/` and `frontend/` have ESLint (`npm run lint`, flat config).
